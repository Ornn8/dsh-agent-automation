# Windows operations

This guide installs local change, review, and maintenance Workers. Pure GitHub coordination jobs run on GitHub-hosted runners; jobs that invoke or inspect a local Agent Worker, plus base reconciliation, run on an exact labeled self-hosted role runner. Repository supervision uses `agent-reviewer`, while Controller recovery uses `agent-maintenance`.

## Runner topology

Two registration modes are supported:

| `registrationScope` | Local instances | Intended account topology |
| --- | --- | --- |
| `target-repositories` | The configured product-role replicas for every `repositoryMapping`, plus the Controller maintenance replica | Personal accounts and repositories that cannot share an organization runner. This is the example configuration. |
| `organization` | The configured shared product-role replicas, plus the Controller maintenance replica | Organizations whose runner group grants access to every allowlisted target. |

Target-repository instances have deterministic IDs derived from the full repository name plus a short SHA-256 suffix. Each instance has its own GitHub registration, Scheduled Task, runner root, work directory, supervisor log, and fault marker. `operations.roles.<role>.replicas` accepts 1 through 8 and defaults to 1 when omitted. Replica 1 keeps the original instance ID; additional instances append `-r2`, `-r3`, and so on. Runners with the same role label consume independent GitHub jobs concurrently, while workflow concurrency keys still serialize duplicate work for one Issue or pull request. A review job resolves GitHub's selected `RUNNER_NAME` through the installed manifest before it acquires that replica's fixed workspace; callers do not supply or guess a replica identity. The setting is independent of the selected DSH, OpenCode, Claude Code, Codex, or custom Adapter. Stopping one replica does not stop another role, repository, or replica. Organization runners are intentionally shared across all mapped repositories, so repository-level selection is rejected in that mode.

The optional `dsh-web` task is host-wide. Its supervisor probes the loopback RPC endpoint and restarts only the process it started after repeated failures. Every managed Scheduled Task enters the same Windows Role Process Host before it starts a role or Web Host supervisor. That host creates a private desktop, starts the supervisor suspended, assigns it to a kill-on-close Job Object, and only then resumes it. Console and GUI descendants therefore remain off the user's default desktop, and stopping or losing the task host terminates its process tree. This mechanism is Adapter-neutral and applies equally to current and future command-line workers; it is lifecycle containment, not a security sandbox. Any desktop, Job Object, target executable, argument, or working-directory validation failure stops before the supervisor starts and never falls back to the default desktop. Each configured `dsh-web` worker must include nonempty agent and permission preset names plus provider, model, and reasoning effort. The controller creates the session with that DSH agent preset, applies the permission preset through DSH's host-side `commands/execute` endpoint, requires its successful command receipt, applies the complete model selection through `session.selectModel`, verifies the required controller Skill through `skill.list`, and only then submits one structured WorkRequest. The permission command never enters a model turn; a Host without command admission, missing configuration, an unknown preset, plugin registration, or model selection fails before work starts. Plan mode remains an interactive DSH collaboration state and is not enabled for unattended work. Supervisors write per-instance heartbeats, rotate lifecycle logs at 10 MiB with five retained files, and use bounded exponential restart delay; GitHub runner diagnostics remain in each private runner directory.

## Configuration and paths

Use a dedicated Windows account. Install PowerShell 7 (`pwsh`), Git, GitHub CLI, Node, and every Adapter selected by a repository mapping. A `dsh-web` worker requires the DSH Web Host; `opencode-cli` and `claude-code-cli` require their respective executables and existing local authentication. On Windows, configure a native executable rather than a `.cmd`, `.bat`, or `.ps1` command shim because Agent processes start without a command shell. Model credentials remain in those products' local configuration.

Copy [config.minimal.json](../config.minimal.json) to a machine-local file on a data volume, for example `F:\dsh-agent-automation-state\agent-config.json`. Its directory becomes the default `stateRoot`; installed tasks continue to read that file, so it must not remain in a Git checkout. The [configuration reference](configuration-reference.md) lists every optional field and default. A `dsh-web` Worker requires explicit `agentPreset` and `permissionPreset` values, so it never inherits a mutable DSH UI default. Removed fields fail closed rather than receiving implicit migration. The runner must be version 2.334.0 or newer because every reusable workflow uses `job.workflow_repository` and `job.workflow_sha`; the minimal file pins 2.336.0.

Set `github.login` to the exact GitHub CLI login on the host. Install and online doctor call `gh api user` and compare only the login, preventing another cached identity from operating the runners. They do not display the login returned by GitHub or any token.

`operations.roles` is the role admission table. Change and review each accept one through eight Workers; maintenance also accepts a finite list of one through eight Workers. A Worker belongs to exactly one role. `operations.routing` adds ordered, bounded selectors for change and review while preserving the worker-neutral WorkRequest. When omitted, each role receives a default route selecting its first admitted Worker, so PR1 retains the existing single-Worker behavior. Maintenance review also selects only the first candidate from the review default route. A Worker `capacityGroup` defaults to its id when valid as a routing identifier, otherwise to a stable hash of the legacy id; `routingTags` defaults to an empty list. These values are metadata only until a later capacity/failover PR. The loader derives role, implemented Skills, review isolation, executable defaults, and maintenance identity before any Agent starts. Repository mappings contain only a target repository plus nonempty `ciWorkflows[]` and `requiredChecks[]`; the top-level repository list is derived. Changing a role binding is sufficient to replace DSH, Codex, OpenCode, Claude Code, or another Adapter without changing target workflows or GitHub work declarations. The generic `command-json` Adapter and a full-access DSH Worker are change-only. Role replica counts change only local GitHub job capacity; they do not create more Worker definitions or change routing. Install idempotently sets `DSH_AUTOMATION_CI_WORKFLOWS` and `DSH_AUTOMATION_REQUIRED_CHECKS` to compact JSON arrays, plus the trust-bearing `AGENT_AUTOMATION_CONTROLLER_LOGIN` projection of `github.login`. The login projection must match the configured identity; the JSON values are routing configuration, not secrets, and uninstall intentionally retains them.

For `opencode-cli`, select the existing `provider/model` and variant. The role table derives mode, capabilities, and the review Git executable. The Adapter discovers no repository-local OpenCode configuration: it mounts the controller-owned Skill in a temporary configuration directory. Review additionally uses OpenCode's `--pure` mode, disables default and Claude Code plugin discovery, and supplies a temporary primary agent that denies edits, shell commands, subagents, network tools, language servers, and questions while removing GitHub and provider-key environment variables. OpenCode's `--auto` flag therefore removes interactive prompts only for operations that the explicit review policy has not denied.

Run a real OpenCode adapter/provider smoke explicitly after installing or changing that adapter. The smoke creates a temporary two-commit repository, invokes the read-only review adapter with the selected provider, model, and variant, validates OpenCode's NDJSON session output, and deletes the repository. It is intentionally outside the default test suite because it consumes provider quota. With a temporary OpenCode CLI supplied by npm and a DeepSeek environment credential, run `npx --yes --package opencode-ai -- npm run smoke:opencode`; override `OPENCODE_SMOKE_EXECUTABLE`, `OPENCODE_SMOKE_MODEL`, `OPENCODE_SMOKE_VARIANT`, or `OPENCODE_SMOKE_CREDENTIAL_ENV` when the deployment uses different values. The script forwards only the named provider credential into the otherwise isolated reviewer environment and never prints its value.

For `claude-code-cli`, select model and effort. The role table derives mode, capabilities, and the review Git executable. Change mode loads a temporary controller plugin and starts with `bypassPermissions`; use it only for the trusted change queue. Review disables Slash Commands, loads only the neutral project setting source, disables CLAUDE.md and auto memory, uses `dontAsk` with a fixed `Read,Glob,Grep` tool set, supplies a strict empty MCP configuration, disables Chrome, and removes GitHub and provider-key environment variables. It starts outside the pull-request checkout and receives only the controller review Skill, exact-pair input, and read-only additional directory.

On Windows, `installRoot`, `stateRoot`, and `logsRoot` must be local absolute non-`C:` paths. The scripts reject `C:`, UNC paths, wildcards, volume roots, overlapping roots, mappings beyond the per-host limit, generated paths outside the managed roots, and an installed configuration outside `stateRoot`. POSIX dry-run planning accepts native absolute paths and compares them case-sensitively. Windows runtime/state directories are restricted to the installing user and `SYSTEM`. Recursive runtime removal rejects reparse points and operates only on enumerated instance or content-addressed runtime directories.

## Portable installation plans

`doctor.ps1 -DryRun` and `install.ps1 -DryRun` emit a deterministic schema-version-1 document after their readable output. The line starts with `AUTOMATION_INSTALLATION_PLAN_JSON=` and describes paths, the exact platform runner package and checksum, normalized GitHub labels, runner and DSH Web Host services, repository variables, and strict app-bound branch-protection requirements. `bootstrap-repository.ps1 -DryRun` emits `AUTOMATION_BOOTSTRAP_PLAN_JSON=` with every target workflow path, action, and rendered content hash.

Runner artifacts are keyed by `windows-x64`, `windows-arm64`, `linux-x64`, `linux-arm64`, `macos-x64`, or `macos-arm64`. Planning fails when the requested platform has no configured artifact. Platform-owned labels (`self-hosted`, operating system, and architecture) are derived by the plan; role configuration owns only routing labels such as `agent-change` and `agent-reviewer`.

The Windows installer consumes the same plan values for runner instances, labels, paths, archive verification, repository variables, and required checks. `-TargetPlatform` may select another configured artifact only with `-DryRun`. A non-dry invocation rejects a platform mismatch, and non-Windows execution remains unavailable until systemd and launchd lifecycle implementations exist. A non-Windows dry run uses a stable plan-only compiler identity because it cannot inspect the Windows Framework compiler; installation still requires and hashes the real compiler. The plan is a portability interface and test oracle, not a claim that those service managers are already supported.

`stateRoot\install-manifest.json` is the authority for installed runner instances, registrations, exact paths, Scheduled Tasks, DSH Web Host ownership, and the installed operations runtime content hash. It contains no tokens or other credentials. Each supervisor also writes an atomic PID record under `stateRoot\pids`; the record binds the child PID to its exact process start time so PID reuse cannot authorize termination of another process. Keep `stateRoot` when editing mappings, role settings, or registration scope. To move `stateRoot`, first use the old configuration to remove all managed registrations and runtime, then install with the new configuration; a new state root cannot safely discover ownership recorded only in the old one.

Install hashes the operations module, both supervisor scripts, the C# Role Process Host source, and the local .NET Framework compiler. Those hashes determine `installRoot\operations-runtime\<content-hash>`. Install copies the reviewed sources, compiles the WinExe inside a temporary snapshot, records every installed file hash including the generated executable, verifies the snapshot, and only then publishes it atomically. The directory ACL grants the installing user and `SYSTEM` read/execute access; no configuration, credential, runner worktree, or checkout content is copied into it. Scheduled Tasks invoke only the process host and supervisor in that manifest-recorded snapshot, with a validated executable, argument list, and working directory. Switching, updating, moving, or deleting the source checkout therefore cannot silently change an installed service. Separately, install packs the credential-free `dsh-plugin` directory into a content-addressed tarball under `stateRoot\packages`, installs that tarball into the DSH `web` profile with the same CLI that launches the Web Host, and verifies the composed plugin row through `--dump-config` before starting the host.

## GitHub bootstrap permissions

Prefer a GitHub App or a fine-grained, short-lived PAT used through GitHub CLI. Do not place App keys, PATs, ephemeral runner tokens, or model keys in JSON, repository variables, workflow inputs, logs, or PowerShell history.

For `target-repositories`, the bootstrap identity needs each mapped repository's self-hosted runner administration permission, Actions Variables write permission, and repository Administration write permission for default-branch protection. For `organization`, it needs organization self-hosted runner administration and a runner group explicitly granted to every allowlisted target, plus Variables and Administration write permission for each target. A fine-grained PAT therefore needs repository Administration read/write in addition to runner and Variables permissions; a GitHub App installation needs the equivalent repository permissions. The installer fails closed when it cannot read or update required-status-check protection.

The installer requests an ephemeral registration token for each exact organization or target-repository instance and passes it only to that runner's `config.cmd`. Review workers receive no GitHub token. Repository variables are written through `gh variable set`; their values contain no credential material.

Repository setup must also provide the thin forwarding workflow pinned to an immutable controller revision and restrict permission to edit workflows or change protection. Trusted owners, members, and collaborators submit change work with the strict `agent-work:v3` Issue declaration documented in the repository README; valid `agent-work:v2` declarations remain a bounded migration path and use the abstract `default` task class. Opening or editing the Issue schedules ordinary backlog observation; adding `agent/dsh` to an existing Issue schedules an exact re-read followed by a separate controller-authored observation. The label is a wake signal and queue projection, never execution authority. The target workflows must emit the configured aggregate and exact base/head review checks; the installer bootstraps or merges their protection settings. Base reconciliation runs on the change-role runner with its verified host GitHub credential so an update-branch mutation emits the ordinary pull-request events that rerun both CI and review; never substitute the Actions job token, whose mutations suppress those downstream workflows. Keep App/PAT bootstrap credentials out of workflow secrets unless an unrelated workflow requirement explicitly needs one.

Exact-pair squash landing preserves the current pull request body in the squash commit message. After GitHub accepts the merge, the controller re-reads and closes only canonical same-repository Issues in the pull request's closing references, then emits one `agent_backlog_reconcile` repository dispatch. A retry against the same merged pull request reconciles those Issue closures and repeats the idempotent backlog wake-up after a post-merge interruption.

Install normally uses GitHub's [status check protection endpoint](https://docs.github.com/en/rest/branches/branch-protection#update-status-check-protection), preserves unrelated contexts and app-bound checks, sets `strict=true`, and binds both the mapped CI aggregate and exact-head `agent/review` check to the GitHub Actions app ID `15368`. During the pre-release authority-name migration it removes only the exact reserved legacy `codex/review` requirement; unrelated checks remain untouched. If the status-check endpoint returns an explicit `404`, the installer separately checks the full protection endpoint. Only when that endpoint also returns `404` does it use the [full update endpoint](https://docs.github.com/en/rest/branches/branch-protection#update-branch-protection) to create a minimal rule: strict app-bound checks, force pushes and branch deletion disabled, no user/team restrictions, and no manual approval requirement. It therefore does not add a human gate that would block a repository's already enabled GitHub auto-merge policy after the required checks pass. If protection already exists but its status-check facet is absent, install only attempts the narrow status-check update and fails closed if GitHub rejects it; it never reconstructs or overwrites existing review, restriction, history, or conversation rules. Every write is read back and verified. Uninstall never removes or relaxes protection. A landing Profile that selects `source: branch-protection` does not read this Administration endpoint with the workflow token. It requires a clean exact head, a trusted exact-pair review, and a successful merge response; GitHub enforces the installed branch rule atomically at that merge request. Explicit check-name Profiles still read the configured protection facet to preserve app binding. This automation supports GitHub.com only: the controller's reusable-workflow provenance depends on `job.workflow_repository` and `job.workflow_sha`, introduced for runner 2.334.0 and unavailable on GitHub Enterprise Server.

The `codex/review` to `agent/review` migration is intentionally atomic. Publish the controller revision containing `agent-review.yml`, render and publish the target workflows pinned to that revision, then run a full install migration so branch protection replaces the reserved legacy requirement. Trigger `Agent Issues` once after publication; its default-branch path reconciles every open same-repository pull request and requests a fresh exact-pair `agent/review`. Existing legacy CheckRuns remain audit history but cannot satisfy the new authority. Do not change branch protection manually or pin a controller revision that lacks the new workflow path.

## Offline target workflow bootstrap

`bootstrap-repository.ps1` renders only the nine thin forwarding workflows under a local target checkout's `.github/workflows/` directory, including scheduled repository supervision and hosted landing reconciliation. It does not invoke GitHub CLI, read credentials, set repository variables, stage files, commit, or push. Supply the controller's owner/name, a published lowercase 40-character `ControllerSha` that remains permanently reachable from the controller default branch, the configured CI workflow names, and the exact upstream owner/repository audited by supervision. If a controller PR is squash- or rebase-merged, verify that the published commit tree exactly matches the reviewed PR-head tree before pinning the published commit; never pin a PR head from a branch that may be deleted. The offline renderer does not verify GitHub reachability.

GitHub does not start ordinary downstream workflows for labels written by a workflow's own `GITHUB_TOKEN`. Issue opened, reopened, and edited events reevaluate `agent-work:v3` and the bounded `agent-work:v2` migration form; backlog, reconciliation, and bounded recovery use the supported `repository_dispatch` exception for their Issue and exact-pair review handoffs. An `agent_work_requested` dispatch carries the complete WorkRequest under the single `client_payload.work_request` property so Profile extensions do not consume GitHub's bounded top-level payload properties. The Controller records a handoff as applied only after GitHub accepts that dispatch; a retry retains the same request ID for Worker-side deduplication. Target listeners live on the protected default branch, reusable jobs remain pinned to the published controller SHA, and each worker revalidates the live Issue or exact pull request base/head before any model call. Labels remain observable audit state, never independent execution authority.

```powershell
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\bootstrap-repository.ps1 `
  -TargetCheckout F:\target-repository `
  -ControllerRepository Ornn8/dsh-agent-automation `
  -ControllerSha 0123456789abcdef0123456789abcdef01234567 `
  -CiWorkflowNamesJson '["Target CI","Security"]' `
  -UpstreamRepository deepseek-ai/deepseek-harness `
  -DryRun
```

The checkout argument must name the local Git root exactly. The renderer validates every generated workflow and every staged, unstaged, or untracked overlap before writing any file; use `-Update` only after reviewing that exact replacement. A matching rerun writes nothing. CI repair and advancement accept only workflow names in `DSH_AUTOMATION_CI_WORKFLOWS`; advancement evaluates every check in `DSH_AUTOMATION_REQUIRED_CHECKS`, while privileged landing independently rereads exact-head evidence and lets GitHub enforce branch protection at the exact-head merge. A `workflow_run` caller transports its run id and attempt, not a mutable `pull_requests[0]` entry; the Controller verifies the completed review run and exact CheckRun before it derives the PR subject. Pull-request updates, CI completion, review publication, repair completion, resume, and explicit landing requests wake advancement directly; hosted reconciliation repeats the same read-and-decide path every 15 minutes only to recover an omitted event. Rework preserves the exact failed workflow name through recovery, and repository supervision runs an offset six-hour schedule plus a manual dry-run entry point. The generated health workflow runs a hosted queued-job watchdog hourly and real change/review provider canaries daily; manual dispatch remains available. Set the three target projections through the installer or repository settings before committing the generated files.

Controller promotion is a separate reviewed change. Prepare a snapshot with `activeProductPullRequests`, then run `node src/promote-controller.mjs --record controller-release.json --candidate <published-sha> --snapshot <snapshot.json>`. Active product work freezes normal promotion; the pending array is an explicitly latest-only slot, and the command reports every older candidate superseded by a defer or promotion. One ordinary promotion may consume each UTC day. A fault-bound promotion additionally requires `--fault-record <record.json>` proving the current epoch is deploying after one repair PR, independent PASS, and CI success; it bypasses the freeze once for that root fault and consumes that UTC day's ordinary slot. Later ordinary candidates remain in the latest-only slot until another day. Do not promote after every repair: target repositories reconcile every published Controller pin as a real default-branch change. No generic emergency flag exists.

Host-credential change and repair runs append an `agent-controller-mutation:v1` marker to their durable status comment. The marker binds the target subject to the exact target Actions run and reusable Controller path/SHA so intervention measurement can distinguish a Controller operation from an unmarked operator mutation. It is audit evidence only; it never authorizes execution. Base reconciliation continues to use its independently attested Governor record, and maintenance uses its FaultRecord attestation.

The pre-batching Governor measurement is stored in [`metrics/governor-baseline-2026-08-17.json`](metrics/governor-baseline-2026-08-17.json). Repeat the same completed-root and reached-PR denominators after ten friendly-repository WorkRequests. During those ten runs, record the interval between trusted progress events without enforcing a timeout; select the unattended liveness limit from that distribution before freezing the Controller revision for the hostile-repository run. The final three friendly WorkRequests must use one Controller revision even though the full friendly window may cross revisions.

## Infrastructure recovery and circuits

The Controller-owned `.github/agent-automation/profiles/controller-maintenance.json` configures deterministic actions, backoff, maintenance procedure, allowed paths, independent review, CI timeout, promotion, verification, resume, concurrency, and fixed upper limits. `controller-maintenance.yml` advances recovery every 15 minutes. The separate `controller-maintenance-readiness.yml` verifies the exact maintenance replica, Worker CLIs, and dedicated Controller credentials every 15 minutes without a model; one daily readiness run invokes one available maintenance provider canary. The hosted runner watchdog accepts four nominal schedule intervals, or 60 minutes, for either maintenance workflow so GitHub schedule and promotion jitter does not invalidate a healthy replica; its separate queued-job check remains 20 minutes. `AGENT_AUTOMATION_MAINTENANCE_REPLICA_ID` is trust-bearing repository configuration: the installer and doctor bind it to the one configured maintenance instance, and a hosted preflight rejects a missing or malformed route before any privileged job can queue. Protect repository-variable administration accordingly. A readiness failure therefore cannot invalidate FaultRecord transitions written by the recovery workflow.

The target `Agent Recovery` workflow first calls the GitHub-hosted fault observer and then runs bounded recovery even if observation failed. The caller passes the completed workflow's run ID and attempt; the observer reads only the attempt-specific run and jobs API endpoints and rejects a response whose `run_attempt` changed. The observer accepts only an exact failed `pull_request_target` review run bound to the pinned reusable Controller workflow and the single `agent-review / agent/review` reusable job, rereads the live base/head pair, and creates or reopens one `automation/fault` Issue per stable infrastructure identity. A failed sibling caller job cannot become a review-worker fault or change its failure identity or signature. The review job's conclusion, rather than the caller run's aggregate conclusion, selects the infrastructure failure class and code. Before recovery filtering, the observer compares an Actions-owned exact-head `agent/review` CheckRun with the same trusted run, attempt, and pair; a prior-attempt success is not current-attempt evidence. Repository-dispatch runs remain `unknown` because this observer has no trusted input carrying their exact pull-request subject. An authoritative success that contradicts any supported non-success review-job conclusion is audited as `review-evidence-disagreement` and creates no fault, including when the failed job resembles an intentional BLOCK. CheckRun summaries and Error messages remain audit prose and cannot select a verified failure category. This observation path invokes no Agent and does not depend on the failed local review Worker.

Failure classification currently supports two controller-verified roles: configured target required CI and exact-pair Agent review. A verified role is bound to the repository, Actions run ID and attempt, event, exact head or pull-request pair, reusable-workflow references, and a stable signature over the run's jobs and steps; replaying it with a different run, role, or altered evidence fails closed. Required-CI verification reads the expected repository, workflow name, and required check from validated machine `repositoryMappings`; its caller supplies the static workflow route, not an observed run field. The verifier then compares every raw run and CheckRun field with that expected configuration, the fixed GitHub Actions app, the exact subject head, and the run URL. DSH change and repair runs remain `unknown` until a later verification-contract change can bind their exact WorkRequest, subject revision, and receipt evidence. Controller orchestration also remains `unknown` until failed jobs can be bound to an exact reusable-workflow call; run-wide `referenced_workflows`, Error text, and free failure-class strings are insufficient. The closed audit taxonomy reserves `implementation`, `review`, `ci-environment`, `orchestration`, `review-evidence-disagreement`, and fail-closed `unknown` for later shared routing. An intentional BLOCK is audited as `review` and creates no infrastructure fault unless an authoritative successful exact-pair CheckRun contradicts it, in which case disagreement takes precedence. Stale and untrusted pairs emit bounded `unknown`; every classification is emitted before the first fault mutation. This release adds no dispatcher. Successful, active, unqualified cancelled, and failure runs without qualified machine evidence remain `unknown`. Audit evidence records the run ID and evidence signature, limits job and step counts and text lengths, and records omitted counts. The shared recovery policy remains the single authority for intentional review BLOCK recognition.

An infrastructure dead-letter or hosted observation creates or reopens one `automation/fault` Issue per stable fault identity. The Issue is readable projection only. Controller Maintenance accepts only a projection produced by the exact pinned observer or recovery workflow run; successful maintenance runs append trusted `FaultRecord v1` states. One run advances at most one transition per fault. Three deterministic attempts precede the declared maintenance Worker order; each Worker is consumed once per epoch, and only one repair PR may exist. The Controller rereads and path-validates that PR, runs the independent reviewer, verifies functional CI against the fixed Controller workflow path and exact run-bound pull-request pair, rejects candidates that change that workflow, merges the exact head once, installs the exact published runtime snapshot, requires three healthy samples, closes the fault, and wakes the original WorkRequests.

Failure of a repair, review, CI, promotion, or verification is a child attempt of the same root fault. It never creates a new infrastructure Issue. Exhaustion sets `circuit-open`; later schedules perform only model-free health observation. Time, comments, labels, and process restarts cannot open a new epoch. A changed Controller SHA, runtime hash, derived configuration hash, operator-incremented credential generation, failure signature, or three consecutive healthy observations may do so, with no more than three epochs in a rolling 24 hours.

## Governor admission and budgets

Candidate, admitted, attempt, applied, paused, and resumed records are GitHub-visible comments attested by the exact reusable controller workflow run. New implementation work requires a candidate observation and a later independent observation; an execution label or event without the current applied admission fails before a model starts. Review repair, CI repair, workflow recovery, and base reconciliation consume separate subject/work-identity budgets. Controller revision changes do not reset the counters. Exhaustion records `automation/paused` without invoking a model; a trusted exact `/automation resume` comment begins a new bounded epoch.

The 15-minute hosted cycle advances eligible Issue candidates, review repairs, transient review retries, base reconciliation, and deferred landing without model polling. Landing stops after trusted review provenance establishes a non-PASS result; it does not query merge policy or attempt a mutation for a blocked head. A first CI failure performs one deterministic workflow rerun; only a later failed observation can enter CI repair.

Automatic exact-review and failed-CI repair consumes at most six distinct controller-authored status markers for one pull request and one controller SHA. Each marker records the controller SHA and whether it represents automatic review, automatic CI, or explicit human repair. At the limit, the controller writes an English dead-letter status, adds `agent/dsh-failed`, clears automatic repair labels, and exits successfully without invoking a model, so recovery cannot recurse. A trusted explicit rework comment remains independently eligible and does not consume the automatic budget.

A same-head technical rebuttal requests review by adding `automation/review-ready`. The next reviewer receives bounded collaborator responses plus GitHub Actions-owned exact-head check metadata and must address material contrary evidence without treating comments as authorization. Each authoritative review run creates a distinct Governor transition and repair WorkRequest while the generic review-repair budget remains shared. The review listener may consume the label before the repair process resumes; repair therefore records the exact-head review CheckRuns that existed before the Agent started and also accepts a new GitHub Actions-owned `agent/review` CheckRun as proof that the handoff occurred. When a repair advances the head, the Controller emits an exact-head `agent-review` dispatch carrying the admitted Profile, workflow, and review Stage. The CheckRun binds that workflow identity and Profile hash, and landing derives its merge workflow from the CheckRun rather than a caller default. The synchronize listener suppresses only the duplicate default review while `automation/repairing` is projected; the dispatch and CheckRun remain the authorization evidence. An interrupted repair that already advanced the head replays the same deterministic dispatch. A change Worker may rebut one finding once at one head; if the rereview still blocks, it must advance the head with a safe compatibility change or return `cannot-complete` instead of creating a same-head loop.

A CI repair may rerun failed jobs on the same workflow run. Every workflow run has a distinct Governor transition, while its rerun attempts share that transition and all runs consume the generic CI-repair budget. This lets independent configured CI workflows recover on one head without turning each rerun attempt into a new model cycle. Same-head completion requires that exact run id to finish on a later attempt with `success`, the configured workflow name, and the original pull request head; another run or an Agent-reported success is insufficient.

## Validate and install

These checks have no destructive or remote effect:

```powershell
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\test-operations.ps1
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\test-installation-plan.ps1
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\doctor.ps1 -Configuration F:\dsh-agent-automation-state\agent-config.json -Explain -DryRun
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\doctor.ps1 -Configuration F:\dsh-agent-automation-state\agent-config.json -DryRun
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\install.ps1 -Configuration F:\dsh-agent-automation-state\agent-config.json -DryRun
```

The operations suites require Pester 5.7.1 or newer. CI runs the portable installation-plan suite on Ubuntu and Windows, then runs Windows mutation and process-host tests only on Windows. A local host can use `Install-Module Pester -RequiredVersion 5.7.1 -Scope CurrentUser`.

`test-operations.ps1` includes a Windows OS canary that launches a temporary root and child process through the generic host, verifies both use the same non-default desktop with no console window, verifies the target exit code, confirms ordinary Job Object closure terminates a surviving child, and then terminates only a second host to prove the kernel removes that complete target tree. It skips only on non-Windows hosts and removes its temporary directory.

Dry run validates and enumerates the exact instance IDs, service names, operations runtime content hash, and DSH plugin install action. It emits the structured plan, makes no network call, and creates, deletes, registers, starts, or stops nothing. The actual Windows install rejects placeholder login/checksum values, verifies the platform-selected runner archive SHA-256, checks `github.login`, deploys and verifies the immutable operations runtime snapshot, installs the DSH work bundle, sets each selected repository's CI workflow and required-check arrays, merges and verifies its default-branch required checks, and registers only the selected instances:

```powershell
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\install.ps1 -Configuration F:\dsh-agent-automation-state\agent-config.json
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\install.ps1 -Configuration F:\dsh-agent-automation-state\agent-config.json -Roles review -Repositories Ornn8/deepseek-harness
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\doctor.ps1 -Configuration F:\dsh-agent-automation-state\agent-config.json -Online
```

`-Repositories` is available only in `target-repositories` mode. `-NoStart` registers without starting. Existing `.runner` registrations and a hash-identical operations snapshot are retained; task definitions and repository variables are updated idempotently. Install also removes the obsolete exact task `DSH-Agent-Automation-controller` if it exists, without deleting its historical files.

Install compares the desired configuration and current checkout runtime hash with the installed manifest before changing repository variables or runner resources. A removed mapping, registration-scope switch, changed runner name/path, changed or invalid runtime snapshot, or untracked task/directory fails closed. Preview the exact reconciliation, then confirm it explicitly:

```powershell
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\install.ps1 -Configuration F:\dsh-agent-automation-state\agent-config.json -Migrate -DryRun
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\install.ps1 -Configuration F:\dsh-agent-automation-state\agent-config.json -Migrate -ConfirmMigration
```

Migration stops each obsolete instance, verifies its owned process identity, recursively terminates that process tree, removes its exact remote registration, unregisters its exact task, checks the runtime path and every nested item for reparse points, and deletes only that runner root. For an operations-code upgrade, it first stops every retained task, verifies that no task still references the old snapshot, removes that exact snapshot, deploys the new content hash, and re-registers the retained tasks without deleting their runner registration or work directory. Orphan snapshot directories are removed only through this explicit full migration; unknown files or reparse points in the snapshot root fail closed. The manifest is atomically updated after each completed instance so a retry resumes from known state. An untracked artifact whose ID is still desired can be adopted with the same explicit migration flags only when it is not a running legacy task without a PID record. If its ID is no longer desired, restore the previous configuration, adopt it, and then migrate to the new configuration; the scripts do not guess registration ownership.

Migration always reconciles the full configured topology and rejects `-Repositories` or a partial `-Roles` selection. Ordinary idempotent install and uninstall may still select one exact repository/role.

Install creates one private fixed workspace and one lease path for every review replica. The paths are derived from the exact installed replica id under `stateRoot/workspaces` and `stateRoot/workspace-leases`; neither a workflow nor a Worker can provide a reset target. Before a review starts, the controller exclusively leases that slot, cleans its previous tracked and untracked content, fetches the exact base/head pair, checks detached HEAD and merge-base validity, and only then invokes the review Adapter. A live lease causes a bounded defer to scheduled reconciliation instead of an in-process wait. The runner supervisor reclaims dead and expired leases without invoking a model. Normal completion releases the lease in `finally`.

Normal doctor reconciles the desired instances with the manifest and discovered tasks/directories, verifies every runtime file hash and every task's exact snapshot script path, then checks every expected ACL, task/PID pair, fresh heartbeat, review workspace and lease, executable, obsolete-controller state, and DSH Web Host task/PID pair. A deliberately offline manifest entry does not require a heartbeat. A different checkout hash is reported as a required explicit migration; it does not alter the running snapshot. `-Online` additionally verifies the GitHub principal, all mapped repository projections, every app-bound required check, and the loopback DSH RPC health endpoint, including the active provider, model, and reasoning effort advertised for each matching `dsh-web` worker. It diagnoses only; it does not repair or restart anything. `-Explain -DryRun` instead prints every effective local value with its source file and line plus every planned review slot. `-Explain` also reads the repository variables, shows their declared and effective values, reports live slot state without reclaiming it, and fails when a required projection is missing or the controller login differs.

Heartbeat timestamps are parsed as UTC independently of the host time zone. A fresh supervisor heartbeat therefore has the same readiness meaning on UTC and non-UTC Windows hosts.

## Exact service control and fault injection

In target-repository mode, a worker command requires its repository. `-Replica` defaults to 1 and selects one exact runner:

```powershell
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\control.ps1 -Configuration F:\dsh-agent-automation-state\agent-config.json -Component review -Repository Ornn8/deepseek-harness -Action status
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\control.ps1 -Configuration F:\dsh-agent-automation-state\agent-config.json -Component change -Repository Ornn8/deepseek-harness -Action restart
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\control.ps1 -Configuration F:\dsh-agent-automation-state\agent-config.json -Component change -Repository Ornn8/deepseek-harness -Replica 2 -Action status
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\control.ps1 -Configuration F:\dsh-agent-automation-state\agent-config.json -Component review -Repository Ornn8/deepseek-harness -Action fault
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\control.ps1 -Configuration F:\dsh-agent-automation-state\agent-config.json -Component dsh-web -Action restart
```

In organization mode, omit `-Repository` and use `-Replica` when selecting a replica after the first. `fault` writes one marker within the private state root; only the selected supervisor consumes it and restarts its owned process. It does not modify a checkout or GitHub job. Do not inject a fault during work that must complete.

`stop` and `restart` first prevent the exact Scheduled Task from relaunching, then recursively terminate only the PID tree named by that instance's record and wait for both the task and owned root process to exit. `start`, `restart`, and fault injection require the manifest snapshot hashes and task script path to verify first; `stop` remains available to contain a damaged installation. `start` is idempotent when the task and PID record already agree. A running task without a valid ownership record, a reused PID, or an unreconciled manifest is an error; the scripts will not use a name-based process kill. These rules keep stopping one repository/role independent from all other instances.

## Uninstall and recovery

Inspect the exact scope first:

```powershell
pwsh -NoProfile -File F:\dsh-agent-automation\scripts\uninstall.ps1 -Configuration F:\dsh-agent-automation-state\agent-config.json -Roles review -Repositories Ornn8/deepseek-harness -ConfirmRemoval -DryRun
```

Actual uninstall requires `-ConfirmRemoval` and refuses unreconciled desired/installed state; run the explicit install migration first after a mapping or scope change. It stops and confirms the recursive exit of only each enumerated instance's owned process tree, then removes its exact task. The default retains the manifest entry, runner registration, shared operations snapshot, DSH plugin profile entry, and content-addressed plugin tarball as an intentionally offline installation, so reinstall can restore the task idempotently and stopping this controller does not modify the user's DSH composition. Add `-RemoveRunnerRegistration` to remove the matching remote registration. `-PurgeRuntime` requires `-RemoveRunnerRegistration`; after both succeed, uninstall deletes only the checked non-reparse runner directory and removes that entry from the manifest. The content-addressed operations snapshot is deleted only when `-PurgeRuntime` has removed the last runner entry and DSH Web Host is no longer managed; configuration and credentials are never part of that deletion. `-RemoveDshWebHost` applies the same owned-process stop rule to the host-wide task. Logs, work directories, machine-local configuration, CI routing variables, and branch-protection checks are always retained for audit and recovery.

If bootstrap or health checks fail, keep the runtime intact, run online doctor, and inspect the exact instance log. Re-run install after correction; instance IDs, paths, tasks, variables, and retained registrations are deterministic and idempotent.

PR3 defines closed Adapter failure observations and pure CapacityRecord transitions. PR4-B activates runtime routing failover through the dependent durable registry while keeping failure observations bounded and provider-neutral.

The dependent durable registry is local to one `operations.stateRoot`. It persists immutable fenced record snapshots and bounded attempt events. It uses a canonical exclusive lock plus a fixed reclaim marker, private-file write, sync, close, and atomic publish for snapshots and leases; compaction never removes a newer fencing generation. A stale reclaimer must first own the fixed marker, and normal owners never create the canonical lock while that marker is present. Marker takeover uses one fixed quarantine path, so crashed reclaimers leave bounded residue and cannot remove a newer owner. Lock-layer ownership loss fails the single operation instead of replaying its callback. Readers retry identifiable `ENOENT`, `EPERM`, or `EBUSY` sharing races during compaction, then re-enumerate the base and event families together before selecting the stable highest-fence journal; unrelated filesystem errors remain failures. A capacity record key is an opaque bounded digest of the complete trusted capacity group and provider/model/Worker identity tuple for its scope. Runtime routing claims all expired applicable scope records for a candidate in one lock transaction and publishes no lease when a scope cannot be claimed; the Worker router closes all leases in a finalization path. Durable records remain policy state and do not replace the trusted WorkRequest or route decision.
